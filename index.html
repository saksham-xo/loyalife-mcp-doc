01

MCP, in plain terms

AI that can only talk

You ask a question
↓
AI answers from what it already knowsit cannot check anything, or act

AI that can talk + act

You ask a question
↓
AI looks something up or takes an action in Loyalifethen answers with real, current, permission-checked information

MCP (Model Context Protocol) is the standard that makes the second kind possible — think of it the way you'd think of a plug shape: an agreed interface so any AI assistant and any piece of software can talk to each other without a custom, one-off integration every time.

The one thing to never forget: MCP does not make the AI all-powerful inside Loyalife. It gives it a controlled way to use specific things Loyalife already lets it use — nothing more.

02

What is the Loyalife MCP, specifically?

It's a second front door into the platform — sitting alongside the existing admin console, not replacing it.

AI Assistant Claude, ChatGPT, Copilot, other agents
↓
Loyalife MCP Server the controlled interface
↓
Loyalife's existing services RBAC, members, config, campaigns…
↓
The same database & business logic the admin console already uses

The MCP talks to the same services that an admin/user can already use from the frontend in the admin console.

The AI and your browser never share each other's login details directly — a background handshake (Section 4) keeps the two connected without either side seeing the other's credentials.

03

How a request travels

① You ask the AI assistant something
↓
② The AI figures out what you're asking for
↓
③ It checks whether a Loyalife tool can help
↓
④ Loyalife confirms who you are & what you're allowed to do
↓
⑤ The capability runs — a lookup, a search, an action
↓
⑥ The result comes back to the AI
↓
⑦ The AI turns it into a plain-language answer

step ④ happens on every single request — there's no "trusted session" shortcut

04

Access & security

Authentication
Who are you?

You log in once through the normal Loyalife flow. The AI never receives your console password or cookie.

Authorization
Are you allowed to do this?

Your existing role decides which tools the AI can even see — and it's re-checked the instant a tool is called, not just at login.

Session / token
How long is this valid for?

Access expires automatically and refreshes quietly in the background — a live connection won't nag you, but a stale one dies on its own.

Revocation
Can this be shut off?

If an account is locked, deactivated, or program access is pulled, the AI session dies immediately — not "eventually."

Audit log
What happened?

Every session and every tool call is logged: who, what, when, and whether it succeeded.

Rate limiting
Is this happening too fast?

Independent limits per person, per program, and per login attempt stop runaway or abusive use — including a loop the AI itself might get stuck in.

A tool the AI can't see doesn't exist to it. If your role lacks permission, the AI isn't offered that tool at all — it's not that it tries and gets denied, it's never on the menu.

CAN

  • Use specific capabilities that have been exposed as tools
  • Retrieve information you're permitted to see
  • Perform permitted actions, logged as they happen
  • Work with the structured inputs/outputs each tool defines

CANNOT

  • Access anything not explicitly exposed as a tool
  • See or do anything your role doesn't permit
  • Bypass RBAC, validation, or business rules
  • Grant itself more access than you actually have
  • Replace the console or underlying services

Before MCP vs. after MCP

Before

You have a question
↓
Figure out which screen or report has it
↓
Navigate there, or ask engineering / another PM
↓
Retrieve raw data, interpret it yourself
↓
Manually do the next step

After

You have a question
↓
Ask the AI assistant directly
↓
It identifies the right tool
↓
Loyalife runs the permitted lookup/action
↓
AI explains the result in plain language

What this removes: manual navigation across screens, context-switching, repetitive lookups, and needing to know exactly which report or API has the answer.

What it does not remove: permissions, business rules, validation, approval steps, or the need for a capability to exist as an exposed tool in the first place. MCP removes the legwork around governance — it doesn't skip governance.

07

Where MCP can save us from building another feature

The important distinction: MCP does not create capabilities. If the underlying Loyalife data or operation exists and can be safely exposed as a tool, we may be able to reach it through AI without building a dedicated experience for every use case.

Simple examples, today

🔎
Find information
"Show me this member's redemption history"
A read-only tool looks up and returns the data.
📊
Understand data
"How many members are in Tier 2 right now?"
A read tool aggregates and returns a count.
⚙️
Perform an action
"Approve this anomaly transaction"
A write tool performs the action — same permission checks, fully logged.
🧩
Configure something
"Update this tier's qualification method"
A write tool changes program config, same as doing it in the console.

Example 1: bulk campaign creation from a spec

A spreadsheet defines a batch of campaigns — name, rules, dates, target segment, one row per campaign. Today, someone builds each one by hand in the console. With MCP, Claude reads the spec and creates them directly — the same pattern already used to bulk-configure member attributes.

Spreadsheet with campaign definitions — one row per campaign
↓
Claude reads the spec and maps each row to Loyalife's campaign & rule fields
↓
MCP tools create each campaign and its rules, one at a time, permission-checked
↓
Claude reports back what was created — and flags anything it couldn't map cleanly

This is an example of a real feature that doesn't need to be built as a Loyalife feature. MCP already exposes what it needs.

Example 2: bulk claims approval from a review list

A CS lead has already reviewed a batch of claims and knows which should be approved and which declined. Today, that means opening the approvals queue and clicking through them one at a time. With MCP, Claude works through the list directly.

List of claim IDs with approve/decline decisions already made
↓
Claude looks up each claim's current status and flags any that don't match expectations
↓
MCP tools approve or decline each one, permission-checked and logged
↓
Claude reports back what went through — and what it skipped or flagged

This is an example of another real feature that doesn't need to be built as a Loyalife feature. MCP already exposes what it needs.

Who actually uses this?

Many enterprise clients — banks especially — spend little time in the admin console themselves. Internal Loyalife teams are likely the first real users of MCP.

Demo / Pre-sales

  • Pull program/campaign details live to answer a prospect's question
  • Walk through a sample member's journey during a pitch
  • Seed sample data for a tailored demo

Arguably the strongest pitch moment: demonstrating an AI-assisted conversation with Loyalife, live, is itself the demo.

Implementation

  • Answer "how is this currently configured?" during setup
  • Spot-check tier/rule/fraud config against expectations
  • Make small config adjustments during setup

Customer Success

  • "How is this program configured?" without even opening the Loyalife admin console
  • Investigate a client's member/program question directly
  • Assemble a performance-trend view from existing data

A great day-to-day timesaver.

Customer Support

  • Gather member/transaction/rule context before responding
  • Check anomaly/fraud flags on a disputed transaction

Speeds up investigation. A real backend bug can now get escalated to engineering — and with better evidence attached.

What MCP is not

✕ An AI model itself — it's not Claude or ChatGPT, it's what connects them to Loyalife
✕ A replacement for Loyalife's backend services
✕ Unrestricted database access
✕ A way to get every Loyalife capability "for free"
✕ A way to bypass login, permissions, or business rules
✕ A way for the AI to grant itself more access than the requesting user has

10

Terms you'll actually need

MCP
The standard that lets an AI call external tools.
Why care: it's the "how" behind every AI–Loyalife interaction.
Tool
One specific, exposed capability — e.g. "look up a member."
Why care: this is the unit you'll scope when requesting a new AI-usable capability.
Authentication
Confirming who you are.
Why care: happens once, through the normal login.
Authorization (RBAC)
Confirming what you're allowed to do.
Why care: checked live, every single call — not just at login.
Session
The record of "you're currently connected."
Why care: it has a lifespan and dies if you're deactivated.
Access token
A short-lived pass the AI uses to make requests.
Why care: expires automatically within roughly an hour.
Refresh token
A longer-lived credential used to get a new access token silently.
Why care: valid ~30 days, single-use each time.
Rate limiting
Caps on how many requests can happen in a given time.
Why care: prevents abuse or a runaway automated loop.
Audit log
The record of every session and every tool call.
Why care: how "what did the AI actually do" gets answered later.
Revocation
Killing access before it would naturally expire.
Why care: instant if an account or program is locked.

Setting it up

Captured Example: Connecting to a QA program.

Admin side: turn MCP on

1. Make MCP visible for the program

Applies the same way on QA, EU, or IN. Go to the Base Program → Platform Config → Program Level Settings, pick the program, open Module Config, and turn on "AI agent access." This just makes the MCP option show up in that program's own settings — it doesn't connect anything yet.

2. Turn MCP on inside the program

Open that program directly → Program Settings → Modules → MCP, and choose which AI agents can connect. Works best with Claude.

Connecting from Claude

3. Log in to Loyalife

4. In Claude, go to Settings → Connectors, search "Loyalife," and hit Connect

5. Accept the redirect, then authorize on the screen that follows

6. Select the program to connect

7. If MCP isn't enabled for that program, an admin turns it on first

This is steps 1 & 2 above, done for that program.

8. You're redirected back to Claude

9. Verify — from Claude Settings, or Claude Code's installed plugins

The big picture

AI / LLMUnderstands user intent
↓
MCPControlled interface to specific, permitted tools
↓
LOYALIFEData + business logic + services + permissions

The one sentence to remember: MCP doesn't make Loyalife itself intelligent. It gives an AI assistant a controlled, permission-checked way to interact with the specific capabilities we choose to expose — nothing more, nothing less.

Practically, that means the useful question for a PM isn't "where do we put the AI?" — it's "what capability should we expose, to whom, and under what conditions?" The nearest-term proving ground for that is probably our own teams, not client admins; the longer-term opportunity, including in enterprise conversations, still depends on the same fundamentals — permissions, auditability, and capabilities that are actually built and exposed.
